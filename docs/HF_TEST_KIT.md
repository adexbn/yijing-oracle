# Hugging Face 侧模型对比测试包（高通先行版）

用途：把现役端侧模型与候选模型放到 Hugging Face 上跑**同一批固定题目**，逐条对齐看输出质量，
为「Android（高通）端侧模型是否要从 `Qwen3-1.7B` 换成 `Qwen3.5-2B`」提供实测依据。

最后更新：2026-09-25　生成方式：由仓库源码与既有语料自动导出（问句、卦辞、爻辞均为真实数据，未手写）。

> **硬约束提醒**：本项目**不能关闭思考**（用户原话「不能关闭思考，否则输出质量太差」）。
> 因此两侧都必须在**思考档**下测，不得用关思考的结果做对比。

### 1.3 体积对照（字节数取自仓库 LFS 元数据，已核对）

| 包 | 文件构成 | 合计 | 折合 |
| --- | --- | --- | --- |
| Android 现役 MNN | 5 个文件 | 1 235 520 567 B | ≈1.15 GiB |
| Android 候选 MNN（仅文本） | 6 个文件 | 1 190 614 927 B | ≈1.11 GiB |
| iOS 现役 `Qwen3-1.7B-Q4_K_M.gguf` | 单文件 | 1 282 439 328 B | ≈1.19 GiB |
| iOS 候选 `Qwen3.5-2B-Q4_K_M.gguf` | 单文件 | 1 270 808 032 B | ≈1.18 GiB |

两点实测结论（与最初预期相反，值得先知道）：

1. **换成 2B 不会变大，反而略小** —— iOS 的 Q4_K_M 比现役小约 11.6 MB；Android 的 MNN 文本集合小约 45 MB。
2. **候选 MNN 多一个文件** —— `taobao-mnn/Qwen3.5-2B-MNN` 比 1.7B 那套多出 `llm.mnn.json`（5 344 018 B），
   而且它带视觉分支 `visual.mnn` + `visual.mnn.weight`（合计 196 075 360 B），本项目**不需要**这两个，别一起下。

## 2. 怎么在 HF 上跑

| 方式 | 入口 | 能否开思考 | 能否设采样参数 | 适合 |
| --- | --- | --- | --- | --- |
| 模型页右侧 Chat 框 | 模型页点 `Chat` | 需在消息里带 `/think` | ❌ 用服务端默认 | 快速摸脾气 |
| WebGPU Space（浏览器本地跑） | 第 1.2 节那两条 Space | 需 `/think` | ❌ 一般不可调 | 手上没环境时的首选 |
| 本地 Ollama | `ollama run qwen3.5:2b` / `ollama run qwen3:1.7b` | 可控 | ✅ 全参数可设 | 想省事又不将就 |
| HuggingFace Transformers 本地 | 直接加载两个模型 | ✅ `enable_thinking=True` | ✅ 全参数可设 | **唯一能严格复现 App 的路** |

> 要**严格复现 App 行为**（思考必须开、参数必须一致），只有本地 `transformers` / `llama.cpp` 两条路；
> HF 网页 Chat 与 Space 只能做**粗筛**（看语气、看长文指令跟随、看是否会复读系统提示词）。

## 4. App 用的 SYSTEM 提示词（逐字，与 Android/iOS 完全一致，255 字）

```text
你是一个会解卦的朋友，说话直白、接地气，像跟人当面聊天，不要文绉绉、不要用文言字眼。顺着讲三件事：先说他抽到的卦本身是什么状态、什么性子，用生活里的话讲；再说动的那一爻在提醒什么，把爻辞翻成大白话，讲对他实际意味着什么；最后说变成的卦，点明事情会往哪个方向走。结尾紧扣他问的那件事给几句实在建议，包括该怎么做、要注意和避免什么，要具体到眼下能做的事，别给「积累经验」这类泛泛的话，方向也别和前面的结论打架。全程用「你」称呼他，长度控制在百来字，像聊天一样自然。只输出解读本身，不要复述、解释或提到上面这些要求。
```

来源：`android/app/src/main/java/com/yijing/app/core/LocalAiClient.kt`，iOS 侧 `ios/Yijing/Services/LocalAiClient.swift` 逐字相同。

> 注意：代码库里另有一条「你是精通《周易》的解卦师……不超过 180 字」的 system，那是**云端**路径用的；
> 走端侧本地模型时用的是上面这条。HF 上复现端侧行为请用上面这条。

## 5. 用户消息模板（App 拼装格式，逐字）

```text
所问：{用户输入的一整句话}
本卦：第{n}卦 {卦名}（{上下卦符号，如 ☵☶}）
变卦：第{n}卦 {卦名}（{符号}）
动爻：第 {1-6} 爻
动爻爻辞：{该爻原文}
本卦卦辞：{本卦卦辞原文}
```

来源：`android/.../core/AiClient.kt` 的 `promptOf()`（iOS 同构在 `AiClient.swift`）。

一个可运行的调用等价于：

```python
messages = [{"role": "system", "content": SYSTEM},
            {"role": "user",   "content": USER_MSG}]
text = tok.apply_chat_template(messages, tokenize=False,
                               add_generation_prompt=True, enable_thinking=True)
```

> Qwen3.5-2B 官方默认 **non-thinking**，用 `apply_chat_template` 时必须显式 `enable_thinking=True`；
> 网页对话里则在消息结尾加 **`/think`**。

## 10. 判分口径（沿用 `docs/MODEL_SELECTION.md` 第 4 节）

对每条用例逐条对齐，只看三件事：

1. **是否稳定输出完整解读** —— 有没有跑空、跑满 token 上限、复读题干、退化成「！！！」。
2. **思考段是否真的产生内容** —— 原始输出里 `<think>` 段是否有实质推理（本项目硬约束要求开思考）。
3. **语气与边界是否守住** —— 是否口语化、是否直白接地气、是否泄漏系统提示词或复述要求。

加分观察项：三件事（本卦状态 / 动爻提醒 / 变卦走向）是否都讲到；建议是否具体到眼下能做的事；是否用「你」称呼。

## 12. 已知坑（别踩）

- **HF 网页 Chat 不能设 `presence_penalty` / `temperature`** ⇒ 网页结论只能当粗筛，最终判定要本地跑。
- **Qwen3.5-2B 默认 non-thinking** ⇒ 不加 `/think`（或 `enable_thinking=True`）测出来的必然比现役差，属于测错。
- **两侧参数不能统一** ⇒ Qwen3.5 思考档要 `temp 1.0 + presence_penalty 1.5`，用 0.6 会明显退化。
- **跨端口径不可比** ⇒ 已知 iOS 输出上限 320（v1.2.0 时期）与 Android 768 不同，历史上「iOS 更强」是上限差造成的假象；这次对比要在同参数同上限下做。
- **HF 上的模型不是 App 里的模型** ⇒ 端侧走的是 GGUF（iOS）/ MNN 5 文件（Android）量化版，网页版是 bf16 原版，量化损失需在真机上单独复验。
